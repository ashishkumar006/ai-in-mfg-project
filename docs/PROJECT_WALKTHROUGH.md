# Project Walkthrough

A step-by-step explanation of what the Hybrid AI-Expert System actually
does, from the moment a user fills the dashboard form to the moment
they see a 3D Pareto front. Every step lists **what it does**, **where
the code lives**, and **what the inputs/outputs are**.

---

## The 30-second summary

```
PartSpec  →  CLIPS (rules)  →  ANN (predict)  →  Fuzzy (diagnose)
                                                       ↓
              Dashboard ←  Pareto front  ←  NSGA-II (optimise)
```

Four pipeline stages, one shared data vocabulary (`core/schemas.py`),
the dashboards calling them in order (Streamlit classic + the FastAPI
web UI).

---

## Step 0 — The user fills the form

**Where:** `src/hybrid_ai/dashboard/app.py` (sidebar `_spec_from_form`)

**Input:** a `PartSpec` dataclass from `core/schemas.py`:

```python
PartSpec(
    part_id="SHAFT-A12",
    material="AISI 4140 alloy steel",
    iso_group="P",        # P/M/K/N/S
    operation="turning",  # turning/facing/milling/drilling/boring
    machine="medium",     # light/medium/heavy
    hardness_hb=240.0,
    target_ra_um=1.2,
    batch_size=120,
)
```

When the user presses **Run pipeline**, the dashboard:

1. Loads the shipped blended MLP (`models/nasa_mlp.pt`; trains only if missing)
2. Loads the tool catalog from the in-memory SQLite repository
3. Calls `build_capp_sheet(part, catalog)` from the CLIPS module
4. Renders four tabs: CAPP, Pareto, Diagnosis, Pipeline trace

## Step 1 — CLIPS: rule-based tool selection + CAPP

**Where:** `src/hybrid_ai/stages/clips/rules.py`

**Purpose:** Decide which insert to use and what cutting envelope to
stay inside, before the ANN even runs. This is the "expert system" leg
of the hybrid pipeline — fast, deterministic, fully explainable.

**Inputs:**
- `PartSpec` (the user's part)
- The full tool catalog (a `list[ToolCandidate]`)

**What happens internally:**

1. `_plan_operations(part)` builds a textual CAPP operation plan
   (e.g. for turning: Setup → Roughing → Finishing → Part off →
   In-process inspection → Final QC).
2. `build_rules()` constructs the rule set. Each rule is a `Rule`
   with a name, description, and a Python predicate:
   - **iso-match** — tool's ISO material group must equal the part's
   - **operation-match** — tool's operation must equal the part's
   - **steel-finishing** — for ISO P, if target R_a is tight prefer a
     larger nose radius
   - **heavy-roughing** — heavy machines on P/K allow deeper ap
   - **superalloy-cautious** — for ISO S, require low V_c envelope
3. `select_tools(part, catalog)` keeps only the tools where **every**
   rule returns `True`.
4. `rank_tools(part, candidates)` scores survivors 0..1 by how close
   their envelope midpoint is to a reasonable default
   (V_c≈220 m/min, f≈0.3 mm/rev, ap≈2 mm), with small adjustments
   for superalloys and tight R_a targets.

**Outputs (returned as a 5-tuple):**
- `operations: list[str]` — the CAPP plan
- `candidates: list[ToolCandidate]` — surviving inserts
- `selected: ToolCandidate | None` — top-ranked insert
- `envelope: dict | None` — `{"v_c_mpm": [min, max], "f_mmpr": [min, max], "ap_mm": [min, max]}`
- `notes: list[str]` — planner notes (coolant, finish pass, etc.)

**What the user sees:** the **CAPP tab** — operation plan as a table,
candidates as a sortable dataframe, the chosen insert's geometry, the
recommended envelope, and the planner notes.

## Step 2 — ANN: predict flank wear and surface roughness

**Where:** `src/hybrid_ai/stages/ann/model.py`

**Purpose:** Given the chosen tool and any candidate operating point,
predict the two outcomes we care about:
- `V_B` — flank wear (mm)
- `R_a` — surface roughness (µm)

**Architecture (current):** a 2-layer MLP in PyTorch, configured by
`TrainConfig`:

```python
TrainConfig(epochs=60, batch_size=64, learning_rate=1e-3,
            hidden=(32, 32), seed=42)
```

Internally: `Linear → ReLU → Linear → ReLU → Linear(2)`. Loss is MSE,
optimiser is Adam, input is z-score normalised, target is also
z-score normalised and unnormalised at predict time.

**Inputs (feature vector, 11 dimensions):**

| # | Feature | Source |
|---|---|---|
| 0 | V_c (m/min) | operating point |
| 1 | feed (mm/rev) | operating point |
| 2 | ap (mm) | operating point |
| 3 | nose radius (mm) | selected tool |
| 4 | rake angle (deg) | selected tool |
| 5–9 | ISO group one-hot (P/M/K/N/S) | selected tool |
| 10 | hardness (HB) | part spec |

**Training data:** 1,200 synthetic samples generated by
`core/synthetic.py:generate_synthetic_dataset()`. Each sample is a
random tool + random operating point inside that tool's envelope; the
target is computed from a hand-tuned Taylor-style formula
(`a * (V_c/200)^b * (f/0.3)^c * (ap/2)^0.3`) plus Gaussian noise.
Trains in **~20 s on CPU** for 60 epochs. The dashboard caches the
trained model with `st.cache_resource` so it only trains once per
session.

**Two entry points:**

- `model.predict(X)` — batch prediction on raw feature vectors
- `predict_for_point(model, tool, point, hardness_hb)` — wraps the
  feature-vector construction, clips outputs to physical ranges
  (V_B ∈ [0.02, 1.5] mm, R_a ∈ [0.2, 6.0] µm), and returns a
  `WearPrediction` dataclass with a crude `model_confidence` score.

**What the user sees:** the model's loss curve in the demo, the held-out
RMSE/MAE, and the predicted V_B / R_a at the envelope midpoint in
the **Diagnosis tab**.

## Step 3 — Fuzzy: classify the machining state

**Where:** `src/hybrid_ai/stages/fuzzy/diagnoser.py`

**Purpose:** Turn the ANN's continuous predictions into a discrete,
human-readable state. This is the "interpretability" leg of the
pipeline — the same number can mean different things depending on the
material, and fuzzy logic captures that gracefully.

**Inputs:**
- A `WearPrediction` (V_B, R_a, the tool that was used)
- Optionally a `SensorReading` (vibration RMS in g, current in A,
  acoustic RMS in dB, cutting force in N)
- A `FuzzyThresholds` config with three boundary values per signal

**Membership functions (Mamdani style):**

| Signal | Low | Mid (caution) | High (critical) |
|---|---|---|---|
| V_B (mm) | 0.15 | 0.30 | 0.45 |
| R_a (µm) | 0.8 | 1.6 | 2.4 |
| vibration RMS (g) | 0.8 | 1.5 | 2.2 |

For each signal we compute three memberships over the same bands:
- **fresh** — falling from 1 at `low` to 0 at `mid`
- **caution** — triangular, peaking between `low` and `mid`
- **critical** — rising from 0 at `mid` to 1 at `high`, and staying
  at 1 beyond (never released)

Each signal votes for its strongest membership; the part's state is
the worst vote across the three signals. That rule is monotone: raising
any signal can only worsen the state, and there is no gap between the
bands (an earlier floor rule - "critical needs membership >= 0.3" -
left a hidden "safe" dead zone just above every mid threshold, which
the stress test caught as "midpoint worse than envelope top").

**Outputs:** a `FuzzyDiagnosis` with the chosen state, the three
membership values, and a one-sentence explanation naming the driving
signal, e.g.
*"state=caution; vibration RMS 1.85 g in caution band."*

**What the user sees:** three big metric cards in the **Diagnosis tab**
(state, V_B, R_a), the explanation in an info box, the raw sensor
reading as a table, and a bar chart of the three critical-band
memberships.

## Step 4 — NSGA-II: find the Pareto front

**Where:** `src/hybrid_ai/stages/nsga2/optimiser.py`

**Purpose:** Search the recommended envelope for the cutting
parameters that best trade off three competing objectives:
1. **Maximise MRR** (Material Removal Rate)
2. **Maximise tool life** (estimated from predicted V_B)
3. **Minimise R_a** (surface roughness, predicted by the ANN)

These three can't all be optimised at once — pushing V_c higher
raises MRR but burns the tool faster and roughens the surface. NSGA-II
finds the *non-dominated* set: every point where improving one
objective worsens another.

**Decision variables (3):**
- V_c (m/min) — bounded by `[tool.v_c_min_mpm, tool.v_c_max_mpm]`
- feed (mm/rev) — bounded by `[tool.f_min_mmpr, tool.f_max_mmpr]`
- ap (mm) — bounded by `[0.5, min(tool.ap_max_mm, 4.0)]`

**Objectives (3, all minimised internally):**
- `−MRR = −(ap × f × V_c) / 1000` (cm³/min)
- `−life = −(6.0 / V_B_pred)` (calibrated ~20 min to the 0.3 mm criterion)
- `R_a_pred` (µm)

**Algorithm:** `pymoo`'s `NSGA2` with LHS initialisation, SBX
crossover (η=15), polynomial mutation (η=20), and duplicate
elimination. Default `pop_size=60`, `n_generations=40`. A
deterministic grid sweep is used as a fallback if pymoo is missing.

**Post-processing:** the raw NSGA-II output is filtered by an explicit
non-dominance check (in `_pareto_filter`) to guarantee no point on
the returned front is dominated by another.

**What the user sees:** the **Pareto tab** — an interactive 3D
Plotly scatter (X = MRR, Y = tool life, Z = R_a, colour = R_a,
size = MRR) plus three top-5 tables (by MRR, by life, by R_a). The
sidebar lets the user bump `pop_size` and `n_generations` to trade
quality for speed.

## Step 5 — Feedback loop (and re-planning)

**Where:** the demo's `step 8` and the `dashboard` trace

**Purpose:** When the fuzzy diagnosis comes back as `caution` or
`critical`, the system doesn't just report it — it would send it back
to CLIPS to:

- pick a more wear-resistant insert (different ISO group, coated
  grade, larger nose radius), or
- split the operation into roughing + finishing with two different
  inserts, or
- cap V_c and feed to stay inside the safe envelope.

In the current prototype, this is a *logged* action rather than an
automatic re-run, because re-running NSGA-II inside the dashboard
would block the UI. A future version would call
`build_capp_sheet(part, catalog)` again with a tightened `part` and
merge the new Pareto front with the old.

## The shared data vocabulary

**Where:** `src/hybrid_ai/core/schemas.py`

Every stage talks in the same dataclasses:

| Class | Fields | Produced by | Consumed by |
|---|---|---|---|
| `PartSpec` | part_id, material, iso_group, operation, … | user form | CLIPS |
| `ToolCandidate` | insert_code, ISO group, V_c/f/ap envelope | catalog (SQLite) | CLIPS, ANN, NSGA-II |
| `OperatingPoint` | V_c, f, ap | CLIPS (midpoint), NSGA-II | ANN, Fuzzy |
| `WearPrediction` | V_B, R_a, confidence | ANN | Fuzzy, NSGA-II |
| `FuzzyDiagnosis` | state, memberships, explanation | Fuzzy | dashboard, feedback loop |
| `ParetoSolution` | point, MRR, life, R_a | NSGA-II | dashboard |

This is what keeps the four stages decoupled. You can swap the ANN
for a 1D-CNN or a CNN-LSTM without touching Fuzzy or NSGA-II, as
long as the new model still returns a `WearPrediction`.

## Where the data comes from today

**Synthetic everywhere** — `src/hybrid_ai/core/synthetic.py`:

- `build_default_tool_catalog()` — 15 hardcoded inserts covering
  ISO P / M / K / N / S and turning / facing / milling / drilling / boring
- `generate_synthetic_dataset(n_samples, seed)` — 1,200 fake training
  rows computed from a Taylor-style formula
- `generate_synthetic_sensor(V_c, f, ap, seed)` — a plausible sensor
  reading at a given operating point

The real datasets the project targets:
- **NASA Milling** — 167 runs, V_B + 6 sensor channels, public
- **Sandvik ISO 13399** — tool geometry + speed/feed envelopes
- Optional: PHM 2010 (high-freq), MATWI (multimodal 17.7 GB)

See `docs/IMPLEMENTATION_PLAN.md` for the roadmap to swap synthetic
for real data without changing the pipeline shape.

## How a single dashboard click exercises all four stages

1. User fills the form, presses **Run pipeline** (`dashboard/app.py`).
2. `get_model()` trains the MLP on synthetic data (cached).
3. `get_catalog()` parses the bundled ISO 13399 CSV (50 inserts) into
   the ISO-keyed SQLite store `data/processed/tool_catalog.sqlite` and
   returns it (cached; falls back to the 15-insert built-in list if the
   asset is unreadable).
4. `build_capp_sheet(part, catalog)` runs CLIPS → returns the
   5-tuple.
5. **CAPP tab** is rendered immediately.
6. **Pareto tab** calls `optimise(model, selected_tool, ...)` →
   NSGA-II → 3D Plotly.
7. **Diagnosis tab** calls `predict_for_point(...)` then
   `diagnose(...)` → state + explanation.
8. **Pipeline trace tab** summarises what each stage produced.

Total end-to-end time on a fresh page load: ~25 seconds
(20 s for the cached ANN + ~5 s for NSGA-II).
