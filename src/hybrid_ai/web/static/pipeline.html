From a part description to a safe cutting setting

A machinist says "turn this 4140 steel shaft, I want a decent finish". That single sentence has to become: which insert, how fast, how deep, and is it safe. Four very different kinds of reasoning are needed, and no single method handles all four well — so the system uses four and wires them together.

1

CLIPS rules — what to cut with

Symbolic reasoning · expert knowledge written as if-then rules

A machinist's first question is not "how fast" but "which insert?". That depends on rules a textbook states plainly: a superalloy needs a rigid setup and low speed; a fine finish needs a large nose radius; a heavy machine can take a deeper cut.

What it does

  • Filters the 15-insert catalog by ISO material group and operation
  • Ranks the survivors against group-typical cutting data
  • Returns an envelope: the safe range of speed, feed, depth
  • Emits a CAPP operation plan (setup → rough → finish → inspect)

Why rules, not a neural network

A network could rank inserts from data, but it could not tell you why, and it cannot refuse to answer outside its training distribution. Rules are inspectable and always give a reason.

Tested on all 75 combinations of operation × ISO group × machine class: 42 matched, 33 explained why nothing matched.
IN part spec → insert + envelope + plan
2

Neural network — how worn will it get?

Learned prediction · flank wear VB and roughness Ra

Tool wear is nonlinear. Doubling cutting speed does not double the wear — it compounds it, together with feed and depth. That interaction is exactly what neural networks are good at learning from real machining runs.

What it predicts

  • VB — flank wear in mm, 0 → 1.5
  • Ra — surface roughness in µm, 0.2 → 6.0
  • MC-dropout spread, so the UI can say how sure it is

Outputs are clipped to physically possible ranges — the model can never report wear beyond what a tool could physically reach.

3

Fuzzy logic — safe, caution, or stop?

Fuzzy inference · graded verdicts with a stated reason

Numbers alone do not tell an operator what to do. "Ra = 1.9 µm" is meaningless without knowing the tolerance. Fuzzy logic grades the verdict instead of forcing a hard yes/no, and it scales with the part's own finish requirement.

Three bands, three inputs

Wear, roughness and vibration are each mapped through trapezoids:

InputSafe →Caution →Critical →
VB0.150.300.45 mm
Ra0.81.62.4 µm
Vibration0.81.52.2 g

Ra thresholds scale by target tolerance — asking for 0.8 µm tightens every band.

Why fuzzy instead of a threshold

Hard thresholds make the verdict flip discontinuously: 1.59 µm is "fine", 1.61 µm is "reject". Fuzzy membership degrades smoothly, so a point near the boundary is described as borderline instead of pretending to false confidence.

Every verdict ships with its explanation string — the same wording the operator would use.
IN VB, Ra, vibration, tolerance → state + reason
4

NSGA-II — what is the best trade-off?

Evolutionary optimisation · output vs tool life vs finish

There is no single best cutting setting. Run fast and you get high output but a short tool life and a rougher finish. Run slow and life is long but the cycle time suffers. Optimising one number throws the others away — so this stage returns the whole Pareto front and lets the operator choose.

The three objectives

  • Maximise output — MRR = depth × feed × speed
  • Maximise tool life — from predicted wear
  • Minimise roughness Ra

A genetic algorithm evolves a population of candidate settings, keeps the non-dominated ones, and repeats. The result is a front: every point on it is a genuine trade-off.

The safety interlock

Fuzzy diagnosis is wired in as a hard constraint. When safe-only is on (the default), any setting the diagnoser calls unsafe is infeasible — so the optimiser literally cannot propose a dangerous cut.

Verified: 0 dominated solutions, all points inside the tool envelope, identical results on repeated runs with the same seed.
IN envelope + fuzzy gate → Pareto front of safe settings
✓

Putting it together

Why four methods beat one clever method

Part→Insert + envelope→ VB, Ra→Verdict→ Best trade-offs

Each stage solves the part it is good at and hands a clean, typed result to the next. Crucially the loop is closed: the fuzzy verdict gates the optimiser, and clicking any optimised point re-runs the diagnosis on it, so a recommendation can always be challenged.

What is guaranteed

  • Every displayed number comes from a tool call — none are written by hand
  • Predictions are clipped to physical limits
  • Safe-only is on by default, not opt-in
  • Uncertain regions are flagged rather than hidden
  • Runs fully offline — no API keys, no model downloads

What is honestly uncertain

  • Roughness in the NASA data is imputed, not measured
  • Two comparison models overfit their small training sets
  • The worn-wear band under-predicts — treat near-limit predictions as optimistic
